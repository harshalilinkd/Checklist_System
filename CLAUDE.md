# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A task & checklist management SaaS migrated from Google Sheets to Supabase. Three Node packages, no build step on the frontend.

- **`backend/`** — Express API on `:3000`, talks to Supabase Postgres via the IPv4 pooler. Pulls Supabase Auth JWTs and runs nightly cron jobs.
- **`frontend/`** — Single-file vanilla-JS SPA (`index.html`) served by a tiny `serve.js` static server on `:8080`. Tailwind via CDN, no bundler.
- **`checklist-migration/`** — One-shot scripts for the initial Google Sheets → Postgres migration and Auth user provisioning. Also holds the project's `.env`, which `backend/server.js` loads from here.

The original migration playbook is in [MIGRATION_PROMPTS.md](MIGRATION_PROMPTS.md); deployment to Render is documented in [render-deployment.md](render-deployment.md).

## Common commands

All commands run on Windows PowerShell. The PowerShell execution policy must allow scripts: `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned`.

### Run the app locally

```powershell
# Backend (port 3000) — also loads .env from ../checklist-migration/.env
cd backend
npm install
node server.js     # or `npm run dev` for --watch mode

# Frontend (port 8080) — separate terminal
cd frontend
node serve.js
```

Open `http://localhost:8080`. Sign in with a Supabase Auth user (see provisioning scripts below).

### Migration / Admin scripts

Run from `checklist-migration/`:

```powershell
node scripts/test-connection.js                                 # verify DATABASE_URL works
```

## Architecture

### Data model (in Postgres)

Schema in [checklist-migration/db/001_schema.sql](checklist-migration/db/001_schema.sql). Four tables — **not** generated by a migration framework:

- `doers` — people (`name, department, email`); `email` is the natural FK target.
- `tasks` — recurring definitions (`task_id, frequency, start_date, end_date, doer_email`). `task_id` is a deterministic SHA1 (`t_<hex16>`) of `task_name|email`, so re-imports are idempotent.
- `master_checklist` — one row per **planned occurrence** (`occurrence_key = task_id + '_' + planned_date`). `freq` is **denormalized** from `tasks.frequency` to avoid a join on the hot read path.
- `archive` — same shape as `master_checklist` + `archived_at`. Daily cron moves Done rows older than 30 days here.

### Status is computed, not stored

`master_checklist.status` is a DB column constrained to `('Scheduled','Today','Delayed','Upcoming Focus','Done')`, but **on read** the backend overrides it with a SQL `CASE` expression — see [backend/lib/status.js](backend/lib/status.js):

```sql
case
  when m.status = 'Done' then 'Done'
  when m.planned_date < TODAY then 'Delayed'
  when m.planned_date = TODAY then 'Today'
  when m.planned_date <= TODAY + 7 and m.freq <> 'D' then 'Upcoming Focus'
  else 'Scheduled'
end
```

`TODAY` is `(now() at time zone 'Asia/Kolkata')::date` — see [backend/db.js](backend/db.js) `TODAY_SQL`. **All date math is in IST**, not server UTC. When adding new routes that filter by "today", reuse `TODAY_SQL`.

### Recurrence expansion

When a task is created or extended, [backend/lib/occurrences.js](backend/lib/occurrences.js) generates one `master_checklist` row per scheduled date. Supported frequencies: `D, W, F, M, Q, Y, SM, E1ST..E4TH, ELAST` (frontend currently exposes only `D, W, M, Q, Y`, but the math handles all of them). Inserts use `ON CONFLICT (occurrence_key) DO NOTHING` so re-saving a task or re-running the extension job is idempotent.

### Bootstrap window (the hot path)

`GET /api/bootstrap` returns the user, doers, tasks, and a **windowed slice** of `master_checklist`:

- Window = `planned_date BETWEEN today-10 AND today+30` (constants in [backend/routes/bootstrap.js](backend/routes/bootstrap.js): `WINDOW_DAYS_BEFORE / WINDOW_DAYS_AFTER`)
- Cap at 20,000 rows (`WINDOW_LIMIT`)
- Non-admin users get the rows further filtered by `doer_email = self`
- Frontend then does in-memory filtering for all KPI cards and table views — **does not re-hit `/api/bootstrap` per filter**

This is why the date range matters: anything outside the window won't be in `state.master`. The Scorecard heatmap drill-in uses `GET /api/master/range` to fetch out-of-window rows on demand from `master_checklist + archive` UNIONed.

### Caching

LRU caches in [backend/cache.js](backend/cache.js):
- `masterCache` — 60s TTL, keyed by `${userEmail}:${todayISO}` (cleared on any task / doer / master write)
- `refCache` — 6h TTL for `doers` and `tasks` lists (small, change rarely)

Invalidation is **eager and broad**: any mutation invalidates the entire master cache via `invalidateMaster()`. Don't try to be clever about partial invalidation — the caches are small and the recompute is cheap.

### Auth

[backend/auth.js](backend/auth.js) exports `verifyToken`, `requireAuth` (middleware that 401s without a Bearer token), and `requireAdmin` (403s for non-admin). Admin is determined by **either** `user_metadata.role === 'admin'` in Supabase **or** the email appearing in the `ADMIN_EMAILS` env var — the env var is the runtime override so you can promote someone without re-provisioning.

### Scorecard view (Scorecards tab)

Admin-only per-doer performance report at `GET /api/scorecard/:email?from=&to=`. Computed in [backend/routes/scorecard.js](backend/routes/scorecard.js) — queries `master_checklist + archive` UNIONed (so archived Done rows >30 days old are included).

**Response shape:**
```js
{
  doer, period: { from, to, days },
  kpis: { total, done, delayed, onTime, onTimePct, avgDelayDays,
          bestStreak, currentStreak, completionPct, reliability },
  previousMonth: { ...kpis, period },   // same-length window immediately before
  trend6Months: [ { month, label, onTimePct, done, total } × 6 ],
  dailyBreakdown: [ { date, total, done, onTime, delayed } × N days ],
  freqBreakdown: [ { freq, total, done, onTime, late } × freqs ],
  topTasks: [ { task_id, task_name, count, done, onTime, donePct } × 5 ],
  bestTasks: [ { task_id, task_name, count, onTimePct } × 3 ],   // ≥3 occurrences, ranked by onTimePct desc
  worstTasks: [ /* same shape, asc */ ]
}
```

**Reliability Score (composite 0–100)** — computed backend-side in `routes/scorecard.js`, a weighted blend of three components. Each has a max contribution to the final 100-point score:

| Component | Max pts | Measures | Formula |
|---|---|---|---|
| **On-time** | up to **50** | % of *completed* tasks finished on or before planned | `0.5 × onTimePct` |
| **Throughput** | up to **30** | % of *scheduled* tasks actually completed (done ÷ total) | `0.3 × completionPct` |
| **Consistency** | up to **20** | best on-time streak in the period (30-day streak = max) | `0.2 × min(100, bestStreak/30 × 100)` |

Total: `0.5 × onTimePct + 0.3 × completionPct + 0.2 × streakScore`

**Worked example** (score 72 = 35 + 22 + 15):
- On-time **35/50** → ~70% of completed tasks were on time
- Throughput **22/30** → ~73% of scheduled tasks got done
- Consistency **15/20** → roughly a 23-day best streak
- Total **72/100 → "Strong"**

**Why these three?** Each catches a different failure mode that a single metric would hide:
- High Throughput + Low On-time → finishes everything but always late
- High On-time + Low Throughput → perfect on what they do, skip half the work
- High both + Low Consistency → great averages but erratic, no streak

The frontend renders three progress bars (`On-time / Throughput / Consistency`) next to the score. Bar width = that component's contribution. A short bar = biggest lever to raise the overall score.

**Grade bands** (frontend visual only — backend just returns the raw number):

| Score | Grade | Icon | Color | Plain-English meaning |
|---|---|---|---|---|
| 90–100 | Excellent | `verified` | emerald | top performer |
| 75–89 | Strong | `thumb_up` | emerald | consistently good |
| 60–74 | Steady | `trending_flat` | amber | solid, room to grow |
| 40–59 | Watch | `warning` | amber | warning zone, needs attention — missing tasks or running late often |
| 0–39 | At risk | `priority_high` | red | critical underperformance |

The grade pill in the doer header has a native tooltip showing the scale on hover. It's labeled `cursor-help` + `select-none` to signal "info, not button." **It is not clickable** — purely informational badge that summarizes the numeric score in one word.

**Why Dashboard and Scorecard numbers don't match for the same doer:** they're computed over **different time windows**. Dashboard uses the bootstrap window (today−10..today+30, fixed slice in `state.master`). Scorecard uses **the period you picked** in its date controls (default today−30..today). Same formulas, different slices → different numbers. Not a bug.

**Cross-view doer sync:** `syncDoer(email)` keeps `state.filters.dashDoer` and `state.scorecard.email` in lockstep. Picking a doer on Dashboard, then switching to Scorecards, auto-loads their scorecard. Triggered from:
- Dashboard filter Doer dropdown
- Scorecard filter Doer dropdown
- Leaderboard rows (Dashboard) — clickable, jump to that doer's scorecard
- "View Scorecard →" pill (appears in Dashboard filter footer when a doer is selected)
- "Open Dashboard →" pill (appears in Scorecard preset row when a doer is selected)

**Heatmap click-through:** clicking a day cell in the Scorecard heatmap fetches that day's rows from `GET /api/master/range?email=&from=day&to=day` (since old days are outside the bootstrap window), merges them into `state.master` deduped by `occurrence_key`, then sets master filters (mDoer + mFrom=mTo=day) and switches to Master Checklist.

### Tab visibility

`renderTabs()` filters by `adminOnly` flag. Currently admin-only: **Dashboard, Scorecards, Tasks, Doers**. Non-admin sees only **Master Checklist** (filtered to their own rows). `switchView(id)` defense-in-depth: if a non-admin tries to open an admin-only view (via URL or console), it auto-redirects to `'master'`.

All five `<section id="view-*">` elements start with `hidden` attribute in the HTML so there's no flash of the wrong view between page load and `afterLogin()` completing.

### Financial-year clamp on occurrence generation

[backend/lib/occurrences.js](backend/lib/occurrences.js) hard-clamps every generated occurrence to the window `FY_START..FY_END` (default **2026-04-01 to 2027-03-31**, configurable via env vars). Applied after all other range filters. This means:
- A task with start_date 2025-09-15 only generates occurrences from 2026-04-01 onwards
- The weekly extend-occurrences job won't insert rows past 2027-03-31
- Pre-existing imported rows outside the FY are untouched — only future generation is clamped

### Cron jobs

Registered in `server.js` with `node-cron` (timezone-aware: `Asia/Kolkata`):
- `0 2 * * *` daily — [backend/jobs/archive.js](backend/jobs/archive.js): move `Done` rows where `actual_date < today - 30 days` from `master_checklist` to `archive` in a single CTE+DELETE+INSERT transaction.
- `0 3 * * 0` weekly — [backend/jobs/extend-occurrences.js](backend/jobs/extend-occurrences.js): for active tasks not ending soon, generate the next 12 months of occurrences via the same `generateOccurrences` used at task-create time.

Both jobs are callable on demand: `POST /api/admin/run-job` with `{ job: 'archive' | 'extend' }`.

### Frontend

[frontend/index.html](frontend/index.html) is a single ~2000-line SPA. Tailwind config + custom CSS in the `<head>`; an ES-module `<script>` at the bottom imports `@supabase/supabase-js` from a CDN.

State shape:
```js
state = {
  activeView, session, user,
  doers, tasks, master,    // bootstrap snapshots
  sort, filters,           // master view sort + per-view filter state
  scorecard,               // scorecard view state (email, from, to, data)
}
```

All views render from `state.*` in memory. The only network calls are:
- `/api/bootstrap` on login + on Sync button click (refreshes the snapshot)
- `/api/master/:occurrenceKey/done` on mark-done (optimistic UI in `markDone()`)
- `/api/tasks` / `/api/doers` CRUD from modals
- `/api/master/range` for Scorecard heatmap drill-ins
- `/api/scorecard/:email` for the Scorecards tab

`frontend/app.js` and `frontend/styles.css` are legacy from before the single-file rewrite — `index.html` does not reference them.

### Database connection

`DATABASE_URL` must point at the **transaction pooler** (`aws-1-ap-southeast-1.pooler.supabase.com:6543`), not the direct `db.<ref>.supabase.co` host — the direct host is IPv6-only and won't resolve on most networks. Password's `@` must be URL-encoded as `%40`. See [render-deployment.md](render-deployment.md) for the canonical setup.

Pool is small by default (`max: 5`) because Supabase free tier shares 60 connections across all clients. Configurable via `PG_POOL_MAX`.

`pg` is configured to return `DATE` columns as `'YYYY-MM-DD'` strings rather than JS `Date` objects — see the `types.setTypeParser(1082, v => v)` call in [backend/db.js](backend/db.js). When writing new queries, expect strings.

### CORS + headers

[backend/server.js](backend/server.js):
- `app.set('etag', false)` — JSON responses must always be fresh; Express's default ETag caused 304s that broke `fetch().json()`
- `Cache-Control: no-store` on every `/api/*` response
- CORS origin is `FRONTEND_URL` (comma-separated allowlist) in production, `*` locally

## Conventions to follow

- **Don't introduce a build step.** The single-file frontend + Tailwind CDN is intentional. New chart types should use CSS (`conic-gradient`, flex bars) — see the existing donut and trend charts.
- **Dates: ISO strings (`YYYY-MM-DD`) in code/DB; `DD/MM/YYYY` in UI.** Use `fmtDate()` in the frontend for display.
- **Frontend renders are full re-renders** of each view's container. There's no virtual DOM — heavy lists (Master Checklist) are capped at 500 visible rows (`ROW_CAP`) for performance.
- **Mutations should `invalidateMaster()`** (and `invalidateTasks()` / `invalidateDoers()` if applicable) before returning. Otherwise the frontend Sync button is the only way to see new data.
- **Don't call `/api/bootstrap` per filter change.** All filtering is client-side over `state.master`. Out-of-window data is fetched via `/api/master/range` and merged in.
- **Backend env loading.** `server.js` loads `.env` from `../checklist-migration/.env` deliberately — single source of truth across the two packages. In production, env vars come from Render's dashboard.

## Project-specific gotchas

- The Supabase project ref `hwawiudaevydbglzdync` is **not visible in the Supabase MCP** (different org). Use direct `pg`/script-based access, not the MCP's `apply_migration` or `execute_sql` tools.
- `data/users.csv` has duplicate-email rows that map to different people (e.g. `ea.linkdprints@gmail.com` for both Sushmita and Alisha). Supabase Auth deduplicates by email, so only one survives — the provisioning script keeps the last occurrence and warns.
- `provision-users.js` previously used loose substring matching (`'already' || 'exists' || 'registered'`) to detect duplicates, which produced false positives. It now checks the specific Supabase error codes `email_exists` / `user_already_exists` / HTTP 422.
- The IST timezone offset means rows can appear "delayed" in UTC server time even though they're not in India. Always use `TODAY_SQL` (`now() AT TIME ZONE 'Asia/Kolkata'`) for date comparisons.
- **After deleting data directly via SQL (not through `/api/*` endpoints), restart the backend.** The `refCache` (6h TTL on doers/tasks) won't know about your changes. The UI will keep showing stale data until restart or 6h pass. Mutations through the API call `invalidateDoers()` / `invalidateTasks()` automatically — direct SQL bypasses that. See `scripts/remove-doers.js` for the canonical pattern (preview counts in transaction, single delete, then restart backend).
- **`scripts/remove-doers.js`** removes a doer cascade (master + archive + tasks + doer row) in a single transaction. Pair with **`scripts/remove-auth-users.js`** to also drop their Supabase Auth login accounts. Both scripts are idempotent and report skipped/failed counts.
- **`scripts/check-user.js <email>`** — quick read-only check: is this email in `doers`, has tasks/master/archive, in Auth, in `ADMIN_EMAILS`? Useful before/after cleanup.
